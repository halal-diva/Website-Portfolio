What Actually Happens When You Type a Website Address

You type a web address into your browser, hit enter, and a page appears half a second later. It feels instant and a little bit magic. It isn't magic — it's a lookup system called DNS, and once you see how it works, you'll never look at a URL the same way again.

The problem DNS solves

Computers don't actually think in names like netlify.app. They think in numbers — specifically, IP addresses like 104.198.14.52. That number tells your computer exactly which server on the internet to talk to.

Nobody wants to memorize strings of numbers for every site they visit. So the internet needed a phonebook: something that takes the name you type and hands back the number your computer actually needs. That phonebook is DNS — the Domain Name System.

The four things involved

Before walking through the sequence, it helps to know the four players by name.

Resolver — think of this as the operator you call when you don't know a number. It's usually run by your internet provider or a public service like Google. Its whole job is to go find the answer and hand it back to you.

Nameserver — the actual source of truth for a domain. When someone buys a domain and points it at a hosting company, that hosting company runs a nameserver that knows exactly where that domain should send people.

Record — a single entry in that nameserver's phonebook. There are several types, but two come up constantly:

  • A record — maps a name directly to an IP address ("this name = this number").
  • CNAME record — maps a name to another name instead of a number ("this name = go look up that other name instead"). This is the one hosting platforms love, because it lets them move your site between servers without you ever having to touch anything.

Response — the answer that eventually makes its way back to your browser, telling it exactly where to connect.

The sequence, step by step

Say someone types halimah-yusuf.com into their browser.

  1. The browser asks the resolver. Your device doesn't know the answer, so it asks a resolver, "What's the address for this name?"
  2. The resolver checks if it already knows. Resolvers cache answers for a while so they're not looking everything up from scratch constantly. If it already has a fresh answer sitting in memory, it hands that back immediately and the process ends here.
  3. If not, the resolver goes looking. It works its way through the DNS hierarchy — starting broad (what handles .com addresses?) and narrowing down until it reaches the specific nameserver responsible for the domain.
  4. The nameserver checks its records. This is where the CNAME record matters. If the domain has a CNAME pointing to, say, a Netlify address, the nameserver doesn't hand back a number — it hands back that other name instead.
  5. The resolver follows the trail. Since it got a name and not a number, it now has to look that name up too, which eventually resolves to the hosting provider's actual IP address.
  6. The response comes back. The resolver hands the final IP address back to the browser.
  7. The browser connects. It opens a connection to that IP address, requests the page, and the site loads.

All of this — usually several lookups deep — tends to happen in under a second, often much less thanks to caching.

Why CNAME records matter for a site like this

If a portfolio is hosted on Netlify but you want it to answer to your own domain name instead of the auto-generated one, a CNAME record is the connector. You'd go to wherever you bought the domain, add a CNAME record pointing your domain at Netlify's address, and from then on, anyone typing your domain gets routed through to the site — without ever knowing Netlify is involved at all.

It's the same principle as call forwarding: people dial the number they know, and it quietly connects them to wherever the call actually needs to go.
