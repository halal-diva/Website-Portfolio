Cadence — teaching an AI scheduling assistant to explain itself before it acts.

"When an AI changes your calendar, it should have to explain itself first — that's how it earns your trust."

Problem & User

Two real users want opposite things from the same feature.

Maya wants to see every reason before she'll trust an AI-suggested change. Sarah wants the suggestion to just be right, in under five seconds, with no reading required. Cadence's core design problem was building one recommendation-review screen that genuinely serves both — without pretending the tension doesn't exist.

Maya

Senior PM · Data-Driven Skeptic

Has been burned by cycle-tracking apps that flatten users into generic rules. Refuses to outsource decisions to a black box.

"Show me why. If I can see the reasoning, I can decide if I agree with it."

Sarah

Marketing Director · Friction-Averse

Time-poor parent, zero bandwidth for explanations. Needs the suggestion to be correct, not justified.

"I trust it more if it's right consistently — not because it gave me a paragraph of reasoning."

Research Findings

What the research actually said.

  • 1 Cycle-syncing apps treat cycle-awareness as a bolt-on feature, not a system — none rethink the tool around the user's rhythm.
  • 2 Users consistently distrust predictions based on population averages rather than their own data.
  • 3 Trust breaks down less over "AI" itself and more over rigid systems that expect users to behave consistently — adaptive systems earn more patience.
  • 4 No existing competitor bridges health-tracking rigor with genuine productivity usefulness — that gap became the opening.
IA & Flow Decisions

Reasoning sits beside the decision, not behind it.

The single structural decision the whole project hangs on: the "Why this recommendation?" link is a sibling to Approve/Edit/Decline in the information architecture — reachable before any action is taken, never unlocked only after.

System & Screens

A token-based system, not a one-off UI.

16 components — Button, Input, Card, Modal, Toggle, Phase Badge, Confidence Tag, Reasoning Disclosure, Recommendation Card, and a custom icon set — all bound to design tokens, not hardcoded values, so a single fix (like a contrast failure) propagates everywhere it's used.

Usability Testing + Iterations

Tested with 4 sessions. Fixed what actually broke.

One live moderated walkthrough plus three persona-based scripted sessions surfaced 11 ranked findings. The most severe: when the AI's own reasoning failed to load, the recommendation stayed fully actionable anyway — directly undermining the product's central promise.

AI Workflow

Where AI helped, where it failed, what stayed human.

Tools: Claude (design collaborator + direct Figma plugin scripting) · Figma AI Draft
Helped

Component-accurate screens generated fast once prompts locked exact hex values, radii, and copy. Direct plugin scripting let fixes propagate through real token bindings, not per-screen patches.

Failed

Left unconstrained, it defaulted toward more — a stats dashboard, a batch carousel, a nav bar treating the AI as a separate feature. A style-reference prompt once pulled in pill buttons despite an explicit "don't change components" instruction.

Stayed human

The proof statement. The button-hierarchy reversal. Where reasoning sits structurally. Which usability findings were worth fixing versus logging. AI executed fast — it never decided what mattered.

Looking Back

One decision I'd defend. One I'd change.

Decision I'd Defend

Reasoning as a sibling, never downstream

Testing validated it directly — one participant treated opening the reasoning as non-negotiable before deciding anything; another discovered it completely unprompted. Placing it one tap deeper would have quietly broken the entire thesis.

Thing I'd Do Differently

Design for the user who never opens it

Testing found a real persona type never discovers "Why this recommendation?" at all — and said she likely never would. An unopened trust feature provides zero trust. I'd prototype a lighter-weight trust signal for fast-moving users specifically.
